# Fraud Shield - Database

## 1. Overview

The `database` folder contains all SQL files required for the Fraud Shield project's database.

The database stores information related to:

- Transactions
- Fraud detection results
- Risk indicators
- Fraud explanations
- Machine learning model versions
- Transaction history
- Audit logs

The main purpose of the database is to store, organize, and manage the data used by the Fraud Shield system.

---

## 2. Database Workflow

The basic workflow of the Fraud Shield system is:

Transaction
↓
Fraud Detection Model
↓
Fraud Result
↓
Risk Indicators
↓
Explanation

The system also maintains:

- Model versions and performance
- Transaction history
- Audit logs

---

## 4. Transactions

### File: `transactions.sql`

This table stores the transaction information that is analysed by the Fraud Shield system.

A transaction is the basic input for fraud detection.

### Flow

Transaction
↓
Stored in Database
↓
Sent for Fraud Analysis

---

## 5. Fraud Results

### File: `fraud_result.sql`

This table stores the result generated by the fraud detection system.

It helps the application determine whether a transaction is potentially fraudulent or legitimate.

### Flow

Transaction
↓
Fraud Detection Model
↓
Fraud Result

---

## 6. Risk Indicators

### File: `risk_indicators.sql`

This table stores risk factors associated with a transaction.

Risk indicators help identify why a transaction may be considered suspicious.

Examples may include unusual transaction behaviour or suspicious patterns detected by the system.

### Flow

Transaction
↓
Risk Analysis
↓
Risk Indicators

---

## 7. Explanations

### File: `Explanations.sql`

This table stores explanations related to fraud predictions.

The purpose is to make the prediction easier for users to understand.

Instead of showing only:

`Fraud = TRUE`

the system can provide information about why the transaction was considered risky.

This supports explainable AI and improves model transparency.

### Flow

Fraud Prediction
↓
Explanation
↓
User Understands the Result

---

## 8. Model Versions

### File: `modelversions.sql`

This table stores information about different versions of the machine learning model.

The table contains the following fields:

| Field | Purpose |
|------|---------|
| `id` | Unique ID of the model version |
| `model_name` | Name of the machine learning model |
| `version` | Model version |
| `accuracy` | Accuracy of the model |
| `precision` | Precision of the model |
| `recall` | Recall of the model |
| `f1_score` | F1 score of the model |
| `trained_at` | Date and time when the model was trained |
| `is_active` | Shows whether the model is currently active |

### Why model versions are needed

The fraud detection model may be trained multiple times.

For example:

Model
├── Version 1.0
├── Version 1.1
└── Version 2.0

The database keeps information about each version and its performance.

`is_active` can be used to identify the model currently being used by the system.

## 9. Transaction History

### File: `Transaction_History.sql`

This table maintains historical information related to transactions.

It can be used to:

- Review previous transaction information
- Track changes
- Investigate suspicious activity
- Review past transactions

### Flow

Transaction
↓
Transaction History
↓
Previous Records / Changes

---

## 10. Audit Logs

### File: `Audit_Logs.sql`

Audit logs record important activities performed within the system.

They help track:

- What action happened
- When the action happened
- Which part of the system performed the action
- What was changed

Audit logs are useful for security, monitoring, debugging, and tracking system activity.

### Flow

System Activity
↓
Audit Log
↓
Activity Can Be Reviewed
